# Документация Rogalique

## 1. Общее описание проекта

**Rogalique** — учебный 2D top-down экшен-рогалик на C++/SFML, написанный с нуля вместе с собственным игровым движком.

### Цель проекта

Помимо самой игры, цель проекта — спроектировать и написать небольшой переиспользуемый 2D-движок (`Engine/`) отдельно от игровой логики (`Rogalique/`), на практике разобравшись с компонентной архитектурой, процедурной генерацией уровней, сохранением состояния и базовым игровым ИИ.

### Игровой процесс

Игрок появляется в подземелье, собранном заново при каждом запуске из заранее нарисованных в Tiled комнат. Нужно:

1. Исследовать подземелье, зачищая его от противников (орки, солдаты, слизи) и подбирая снаряжение.
2. Найти 4 ключа (север/юг/восток/запад), разбросанных по карте.
3. Принести ключи к главной двери и открыть её.
4. Пережить на арене за дверью несколько волн врагов подряд.
5. После победы над последней волной — ввести имя для таблицы лидеров (учитывается время прохождения).

Игра в любой момент сохраняется вручную (пауза → «Сохранить») и полностью восстанавливается при следующем запуске — включая то, на какой волне арены игрок остановился.

### Основные особенности

- Процедурная сборка уровня из готовых чанков с детерминированным сидом (см. [раздел 5](#5-алгоритмы-и-важные-технические-решения)).
- Три вида противников с разным поведением и общим ИИ патруля/погони/тревоги.
- Инвентарь на 16 слотов + 8 слотов экипировки, отдельная механика прочности брони.
- Полное сохранение/загрузка состояния, включая бой на арене.
- Таблица лидеров по времени прохождения.
- Настройки (звук, лимит FPS, разрешение, полноэкранный режим), сохраняющиеся между запусками.
- Собственный движок с реестрами коллайдеров/здоровья/камеры, A\*-поиском пути и системой компонентов.

## 2. Установка и запуск

### Требования

- Windows 10/11.
- **Visual Studio 2022** (Community и старше) с компонентом **«Разработка классических приложений на C++»**.
- Ничего больше устанавливать не нужно — SFML 2.5.1 уже собран и лежит в репозитории (`SFML/SFML-2.5.1`), подключается статически. Юнит-тесты движка используют GoogleTest, который подтягивается автоматически через NuGet при первой сборке.

### Сборка из исходников

1. Склонировать репозиторий.
2. Открыть `Rogalique.sln` в Visual Studio.
3. Выбрать конфигурацию **Release | x64** (Debug тоже работает, но заметно медленнее из-за не оптимизированной отрисовки).
4. Собрать решение целиком (`Ctrl+Shift+B`) — соберутся 4 проекта: `SFML` (пустой Makefile-проект, нужен только чтобы SFML было видно в IDE), `Engine` (DLL), `Rogalique` (exe) и `EngineTest` (юнит-тесты).
5. После сборки `Rogalique.exe` появится в `Rogalique/x64/Release/` — пост-билд шаг автоматически копирует туда `Engine.dll` и всю папку `Resources/`, так что папка сборки самодостаточна и её можно целиком скопировать/заархивировать.

Запускать `Rogalique.exe` нужно именно из этой папки (или из соседства с `Resources/`) — все пути к текстурам/звукам/уровням в коде заданы относительно рабочей директории процесса.

### Запуск готовой сборки (без Visual Studio)

Если нужно только поиграть (например, отправить другу), достаточно скопировать содержимое `Rogalique/x64/Release/` (`Rogalique.exe`, `Engine.dll`, `openal32.dll`, `Resources/`) в отдельную папку — Visual Studio для запуска не требуется. Единственная внешняя зависимость времени выполнения — **Visual C++ Redistributable (x64)**, который почти наверняка уже стоит в системе.

### Юнит-тесты

Проект `EngineTest` — консольное приложение на GoogleTest, проверяет вспомогательную математику движка (`Matrix3`). Собирается и запускается как обычный exe (`EngineTest.exe`), отдельного раннера не требует.

### Файлы, создаваемые игрой рядом с exe

| Файл | Назначение |
|---|---|
| `savegame.txt` | Сохранение текущего прохождения (см. [раздел 5](#формат-сохранения)) |
| `display_settings.txt` | Настройки экрана/звука |
| `highscores.txt` | Таблица лидеров |

Все три — обычный текст, отсутствие файла не ошибка (значит «ещё не было»).

## 3. Архитектура

### Разделение на слои

Проект состоит из четырёх Visual Studio-проектов:

| Проект | Тип | Назначение |
|---|---|---|
| `SFML` | Makefile (пустой) | Просто делает исходники SFML видимыми в IDE — ничего не компилирует |
| `Engine` | DLL | Переиспользуемый слой: GameObject/компоненты, окно и рендер, звук, ввод, UI-оверлеи, пространственные структуры (NavGrid, ColliderGrid), логирование |
| `Rogalique` | EXE | Вся игровая логика: конкретные существа, предметы, уровни, меню, сохранение — использует `Engine.dll`, ничего не знает о нём «изнутри» |
| `EngineTest` | EXE | Юнит-тесты движка (GoogleTest) |

Это разделение осознанное: `Engine/` не содержит ничего специфичного для рогалика (никаких «орков» или «зелий») и в теории может быть использован для другой 2D-игры на этом же движке.

### Точка входа и главный цикл

`Rogalique/GameMain.cpp::main()` создаёт `SceneFacade` и вызывает `run()`; единственный верхнеуровневый `try/catch(std::exception)` — последний рубеж перед необработанным крашем (логирует ошибку и выходит с кодом 1, вместо диалога ОС).

`SceneFacade::run()` (`Rogalique/SceneFacade.cpp`) — «композиционный корень» игры: собирает весь мир (уровень, игрока, врагов, предметы, интерактивные объекты), все экраны (главное меню, пауза, инвентарь, настройки, поражение, победа) и передаёт управление в `Engine::run()`. Внутри `Engine::run()` — обычный игровой цикл:

```
TextInputBuffer::clear()
опросить события окна (Closed, TextEntered — остальной ввод polling'ом через sf::Keyboard)
dt = clock.restart()
GameWorld::update(dt)
RenderSystem::beginFrame()
применить активную камеру (единственная запись в реестре, без обхода дерева)
GameWorld::draw()
window.setView(defaultView)   // UI рисуется в экранных, а не мировых координатах
GameWorld::drawUI()
RenderSystem::endFrame()
```

### Компонентный паттерн

Ядро движка — пара `GameObject` + `IComponent` (композиция вместо наследования): игровая сущность — это `GameObject` с деревом дочерних `GameObject` и набором навешенных на него компонентов. Подробный контракт — в [разделе 4](#4-api-и-интерфейсы).

Это решение позволило не городить дерево наследования вида `Actor → MeleeActor → RangedActor → ...` для орка/солдата/слизи — вместо этого каждый вид существа в конструкторе (`Enemy.cpp`/`Soldier.cpp`/`Slime.cpp`) просто набирает нужный ему набор компонентов (`AttackComponent`, `RangedAttackComponent`, `EnemyBehaviorComponent`, ...), и хочет — сочетает их по-своему (например, у Slime3 одновременно и `RangedAttackComponent`, и `AttackComponent` для урона по площади в момент выстрела).

### `GameWorld` — центральный синглтон

`GameWorld` — не просто дерево сцены, а ещё и набор реестров, к которым обращаются компоненты, не имея прямых ссылок друг на друга:

- `getRoot()`/`getUIRoot()` — два независимых дерева (мир в мировых координатах и UI в экранных).
- Флаги состояния игры: `isPaused/isStarted/isGameOver/isVictory/isModalOpen`.
- `getHealthComponents()`, `getColliders()`/`getDynamicColliders()` — плоские списки для перебора (например, `AttackComponent` ищет цель перебором `getHealthComponents()`, а не обходом дерева).
- `getNavGrid()`/`buildNavGrid()` и `queryKinematicColliders()`/`buildColliderGrid()` — пространственные структуры для ИИ и физики (см. [раздел 5](#5-алгоритмы-и-важные-технические-решения)).
- `getActiveCamera()` — одна активная камера, последняя зарегистрированная, а не обход дерева каждый кадр.
- `spawnInRoot()`/`spawnIn(parent, ...)` — **отложенный** спавн: реальное добавление объекта в дерево происходит в начале следующего `update()`, а не немедленно — иначе можно было бы инвалидировать `for`, который в этот момент как раз итерирует список детей выше по стеку вызовов.

## 4. API и интерфейсы

Rogalique не является библиотекой с внешними потребителями — «API» здесь означает внутренние точки расширения `Engine/`, которыми пользуется игровой код `Rogalique/`, и по которым можно добавлять новый контент.

### Контракт компонента — `IComponent`

```cpp
class IComponent {
public:
    virtual ~IComponent() = default;
    virtual void update(sf::Time dt) {}
    virtual void draw(sf::RenderWindow& window) const {}
    virtual void onOwnerMoved(sf::Vector2f newPosition) {}
    virtual void reset() {}

    void setOwner(GameObject* owner);
protected:
    GameObject* getOwner() const;
};
```

Все четыре виртуальных метода **опциональны** (пустые тела по умолчанию) — конкретный компонент переопределяет только то, что ему действительно нужно. `reset()` — не деструктор, а «вернуть в исходное состояние без пересоздания» (используется при возврате в главное меню/загрузке сейва, чтобы не выбрасывать и не пересоздавать все компоненты сцены заново).

### `GameObject`

Ключевые методы:

```cpp
template <typename T, typename... Args>
T& addComponent(Args&&... args); // создаёт, вызывает setOwner + onOwnerMoved, возвращает ссылку

template <typename T>
T* getComponent() const;         // первый подходящий (dynamic_cast), или nullptr

template <typename T>
std::vector<T*> getComponentsInChildren() const; // рекурсивно по всему поддереву

GameObject& addChild(std::unique_ptr<GameObject> child);
void destroyChild(GameObject* child);   // немедленно — нельзя звать во время обхода m_children
void destroyTransientChildren();        // удаляет детей с TransientComponent (см. ниже)
void resetComponents();                 // reset() на каждом компоненте
void destroy();                         // помечает на удаление — реальный снос в конце update() родителя
sf::Vector2f getPosition() const;
void setPosition(sf::Vector2f pos);     // сам зовёт onOwnerMoved у всех компонентов
```

Владение везде выражено через `std::unique_ptr` (и компоненты, и дочерние объекты) — раздельного управления памятью в игровом коде нет.

### `GameWorld` (полный публичный API синглтона)

```cpp
static GameWorld& instance();

GameObject& getRoot();       GameObject& getUIRoot();
bool isPaused() const;       void setPaused(bool);
bool hasStarted() const;     void setStarted(bool);   // false сбрасывает gameOver и victory
bool isModalOpen() const;    void setModalOpen(bool);
bool isGameOver() const;     void setGameOver(bool);
bool isVictory() const;      void setVictory(bool);

void update(sf::Time dt);    void draw();    void drawUI();
void clear();

GameObject& spawnInRoot(std::unique_ptr<GameObject> obj);          // отложенный спавн
GameObject& spawnIn(GameObject& parent, std::unique_ptr<GameObject> obj);

void registerCollider(ColliderComponent*);   void unregisterCollider(ColliderComponent*);
const std::vector<ColliderComponent*>& getColliders() const;
const std::vector<ColliderComponent*>& getDynamicColliders() const;

void registerHealth(HealthComponent*);       void unregisterHealth(HealthComponent*);
const std::vector<HealthComponent*>& getHealthComponents() const;

void registerCamera(CameraComponent*);       void unregisterCamera(CameraComponent*);

```

### Прочие синглтоны

- **`AudioSystem`** — `playMusic(path, loop)`/`stopMusic()`, `loadSound(name, path)`/`playSound(name)` (пул `sf::Sound` с заранее зарезервированной ёмкостью — см. [раздел 5](#5-алгоритмы-и-важные-технические-решения)), `getMusicVolume/setMusicVolume`, `getEffectsVolume/setEffectsVolume`.

### Точки расширения игрового контента

| Хочу добавить... | Что делать |
|---|---|
| Новый вид врага | Скопировать конструктор по образцу `Enemy`/`Soldier`/`Slime`, использовать `addHealthComponentWithFallback()` из `ActorSpawnHelpers.h` для HP/брони и общий `ActorAnimationConfig` |
| Новый интерактивный объект (сундук/дверь-подобный) | Использовать `isPlayerInRangeAndInteractPressed()` из `InteractionHelpers.h` вместо копирования логики «в радиусе + нажата E» |
| Новый предмет | Добавить запись в таблицу `ITEMS` в `ItemDefinition.cpp` (id/название/категория/иконка/бонусы) |
| Новую комнату уровня | Просто положить `.tmj`-файл в `Resources/Level/Chunks/` — `ChunkAssembler` подхватит его автоматически, без правки кода (см. [раздел 5](#5-алгоритмы-и-важные-технические-решения)) |
| Декор/планировку арены | Открыть `Resources/Level/Arena.tmj` в Tiled и редактировать как обычную комнату (слои Floor/Walls/Decor, объекты) — в отличие от комнат подземелья, это единственный файл, а не пул на выбор, и точки спавна волны — свой тип объекта `ArenaSpawnPoint` (см. [раздел 5](#5-алгоритмы-и-важные-технические-решения)) |
| Новый экран/оверлей | Унаследоваться от `IComponent`, взять `OverlayPanelBase` за основу компоновки панели — так сделаны все существующие экраны (`MenuOverlayComponent`, `SettingsOverlayComponent` и т.д.) |

## 5. Алгоритмы и важные технические решения

### Процедурная сборка уровня из чанков

#### Описание алгоритма

Уровень не рисуется целиком вручную и не генерируется тайл-за-тайлом «с нуля» — вместо этого дизайнер рисует в [Tiled Map Editor](https://www.mapeditor.org/) набор небольших законченных комнат-«чанков» (`Resources/Level/Chunks/*.tmj`, каждая 15×15 тайлов с проходом шириной 3 тайла ровно по центру каждой из четырёх сторон) и один неизменный «хаб» (`Resources/Level/rogalique.tmj`, там точка спавна игрока и главная дверь). `ChunkAssembler` во время старта игры:

1. Строит от хаба в каждую из 4 сторон (север/юг/восток/запад) цепочку чанков заданной длины (`chainLength`, по умолчанию 2), на каждом шаге выбирая случайный `.tmj`-файл из папки чанков через `std::mt19937`, инициализированный сидом.
2. Последнее звено каждой цепочки — не случайное, а один из 4 заранее заданных «ключевых» файлов (`keyRoomPaths`) — так игра гарантирует, что все 4 ключа от главной двери физически существуют на карте, а не полагается на то, что случайный выбор их туда положит.
3. Считает смещение каждого куска: перпендикулярно направлению цепочки — центрирование относительно предыдущего куска, вдоль направления — `предыдущий + его размер + длина коридора`.
4. Вычисляет общую bounding-канву всех кусков, сдвигает всё к `(0, 0)` и копирует тайлы/объекты каждого куска в общий массив уровня.
5. `carveCorridor` — повторно проходит ту же арифметику смещений (без хранения явного графа связей между кусками) и прорезает пол и боковые стены в зазорах между соседними кусками, физически соединяя их проходом.
6. `sealEdge` — любая сторона куска, к которой цепочка не выросла (тупик), заделывается стеной — при этом тайл стены берётся из тайлсета **того же самого** куска, а не из общего фолбэка, чтобы заплатка не выглядела чужеродной на чанке с другим оформлением.

Загруженные чанки хранятся в `std::deque<TiledLevel>`, а не в `std::vector` — это осознанный выбор: `PlacedPiece` держит указатель внутрь загруженного чанка, а `deque` (в отличие от `vector`) не инвалидирует указатели на существующие элементы при добавлении новых.

#### Почему так, а не иначе

Полностью процедурная генерация тайл-за-тайлом (классический DFS-лабиринт, BSP-деление и т.п.) даёт бесконечное разнообразие форм, но визуально скучное, безликое подземелье — сложно вручную расставить декор/факелы/ловушки так, чтобы это смотрелось как продуманные комнаты, а не как сетка коридоров. Чисто ручная разметка всего уровня — наоборот, гарантирует качество, но убивает реиграбельность (карта всегда одна и та же).

Гибрид «нарисованные вручную комнаты + случайная сборка» даёт оба свойства сразу: каждая комната выглядит так, как её спроектировал дизайнер в Tiled, а итоговая форма подземелья каждый раз разная за счёт случайного порядка и набора чанков. Дополнительный плюс — расширяемость без программиста: чтобы добавить в игру новую комнату, достаточно нарисовать `.tmj`-файл и положить его в папку, `ChunkAssembler` не хардкодит список комнат в коде.

#### Параметры

- `chainLength` — длина цепочки чанков в каждую сторону от хаба (по умолчанию 2).
- `poolChunkSizeTiles` — размер одного чанка в тайлах (15×15).
- `corridorWidth` — ширина прохода между чанками (3 тайла).
- `seed` — сид `std::mt19937`; тот же сид детерминированно даёт ту же форму уровня. Сохраняется в `GameMemento::levelShapeSeed`, чтобы «Продолжить»/«Загрузить сохранение» пересобрали ровно ту же карту, на которой был сделан сейв.

#### Пример работы алгоритма

```cpp
ChunkAssembler assembler(rogaliqueHubPath, chunksDirectory, keyRoomPaths, seed);
TiledLevel level = assembler.assembleChunkedLevel(chainLength);
```

Результат (лог из реального запуска): `assembleChunkedLevel: собрано 12 чанков вокруг хаба, канва 137x137`.

### Общий поиск цели для ближнего и дальнего боя

`AttackComponent` (ближний бой) и `RangedAttackComponent` (дальний бой) исторически независимо перебирали `GameWorld::getHealthComponents()`, отфильтровывали себя/мёртвых/не подходящих под `targetFilter`, проверяли дистанцию и передний конус обзора — почти дословно одинаковым кодом с отдельно продублированной константой порога конуса. Вынесены в общую функцию `findBestAttackTarget()` (`Engine/TargetFinder.h`) с параметрами диапазона дистанции (`minRange`/`maxRange` — для дальнего боя не ноль, чтобы не стрелять в упор), флагом проверки конуса (выключается для всенаправленных атак вроде слизи) и опциональной проверкой прямой видимости через `NavGrid` (нужна только дальнему бою — снаряд не должен лететь сквозь стену). Один источник истины исключает риск поправить угол обзора в одном компоненте и забыть про второй.

### NavGrid: переиспользуемые буферы вместо переаллокации

Поиск пути (A\*, 8 направлений, без срезания углов по диагонали) строится один раз при старте уровня и дальше статичен. Чтобы не аллоцировать и не обнулять массивы `gScore`/`cameFrom` на каждый вызов (а вызывается он для каждого преследующего бота каждый раз, когда нужно решение), буферы переиспользуются между вызовами через номер «поколения» (`m_searchGeneration`): ячейка считается непосещённой в текущем поиске, если записанный в ней номер поколения не совпадает с текущим — вместо того чтобы каждый раз проходиться по всему массиву и обнулять его.

### Формат сохранения

`GameMemento` сохраняет игру как последовательность необязательных блоков: каждое следующее поле читается только если ВСЕ предыдущие были успешно прочитаны. Это осознанный компромисс ради обратной совместимости: сейв, сделанный до того, как в игру добавили, скажем, инвентарь, всё ещё загружается — просто позже добавленные поля остаются в значениях по умолчанию. Плата за это — жёсткая вложенность (каждое новое поле нужно дописывать строго на своём уровне вложенности одновременно и в `save()`, и в `load()`); при добавлении новых полей это единственное место, где легко ошибиться, поэтому и `save()`, и `load()` в этом файле снабжены плотными комментариями о порядке полей.

### Компоненты вместо наследования

Все виды противников (`Enemy`, `Soldier`, `Slime`) — не подклассы общего `Actor`, а `GameObject` с разным набором навешенных компонентов (`AttackComponent`, `RangedAttackComponent`, `EnemyBehaviorComponent`, ...). Это позволяет свободно комбинировать способности — например, Slime3 одновременно стреляет (`RangedAttackComponent`) и бьёт по площади в момент выстрела (`AttackComponent` с нулевым кулдауном, запускаемый вручную из той же анимационной лямбды) — без множественного наследования или дублирования кода между несвязанными ветками иерархии.

### ИИ противников: вероятностная переоценка вместо проверки каждый кадр

`EnemyBehaviorComponent` реализует конечный автомат `Patrol → Chase → Alert (→ Patrol)` плюс состояние `Rest`. Обнаружение игрока учитывает не только дистанцию, но и конус зрения от направления взгляда врага: в пределах основного угла (±75°) враг видит гарантированно, в расширенном боковом секторе (до ±140°) — только с вероятностью переоценки раз в `PERIPHERAL_REROLL_INTERVAL` (0.5с), а не каждый кадр — иначе реакция врага на игрока, стоящего на границе бокового зрения, заметно «мигала» бы (то замечает, то нет) из-за дрожания угла между соседними кадрами.

### Плавный спавн волн и пауза перед экраном победы

`ArenaWaveComponent` раньше спавнил весь состав волны в один кадр — визуально это читалось как резкий скачок из ниоткуда. Теперь спавн каждой волны разбирается очередью: `spawnWave()` только вычисляет позиции и складывает их в `m_pendingSpawns`, а `update()` вынимает оттуда по одному бойцу раз в `spawnStagger` (порядок и точки спавна вычисляются заранее, чтобы результат не зависел от того, когда именно очередь будет разобрана). `currentWaveCleared()` при этом обязательно проверяет, что очередь пуста — иначе волна могла бы засчитаться выбитой ещё до того, как весь её состав вообще появился на арене. Каждый заспавненный боец дополнительно получает `SpawnFadeComponent` (Engine) — тело и тень плавно проявляются из прозрачности, а не выскакивают на полной непрозрачности сразу.

Тем же компонентом добавлена задержка перед вызовом `onAllWavesCleared` — `victoryDelay`: как только выбита последняя волна, вместо немедленного вызова колбэка запускается таймер, и всё это время мир остаётся не на паузе, чтобы успела доиграть анимация смерти финального врага (босса); только по истечении задержки вызывается сам колбэк, ставящий игру на паузу и открывающий экран ввода имени.

### Арена волн — отдельная Tiled-карта, не код

Арена изначально была написана как два вложенных цикла (пол одним большим спрайтом, стены по клетке) прямо в `SceneFacade.cpp` — редактировать её можно было только правкой C++ и пересборкой. Теперь она такой же `.tmj`-файл, как и комнаты подземелья (`Resources/Level/Arena.tmj`), грузится тем же `loadTiledLevel()` и рисуется той же функцией отрисовки тайлов, что и подземелье, только со своим смещением (`arenaOrigin` вместо `levelOrigin`) — обе карты используют один и тот же код рисования, потому что позиция мировых координат передаётся параметром, а не берётся из захваченной переменной.

В отличие от подземелья, у арены нет случайного выбора и сборки из нескольких кусков — это один фиксированный файл, поэтому `ChunkAssembler` тут не участвует, только `loadTiledLevel()` напрямую. Своя точка отличия — новый тип объекта `ArenaSpawnPoint` (кольцо появления бойцов волны): раньше эти точки вычислялись формулой с отталкиванием от предметов/укрытий, чтобы боец волны не мог заспавниться поверх ящика или в стене; теперь дизайнер расставляет их в Tiled вручную и на глаз, без рантайм-математики — тот же принцип, что уже применялся к `EnemySlot` в обычных комнатах.

### Флип-флаги тайлов Tiled

Формат Tiled кодирует поворот/отражение конкретного тайла в старших 3 битах его GID (Global ID) прямо в данных слоя — отдельно от того, какой это тайл. Изначально движок эти три бита читал только для того, чтобы отбросить их и получить чистый номер тайла (иначе резолв тайлсета по `firstgid` не сработал бы) — сам факт поворота/отражения нигде не сохранялся и никак не использовался. Пока никто не пользовался этими кнопками в Tiled, это было незаметно; как только в новых комнатах подземелья (room8, room9) появились тайлы с флагом Flip Horizontally/Vertically/Rotate (например, декоративная цепь, зеркально повторяющая один и тот же кадр вертикальной полосой), стало видно, что они рисуются в своей исходной ориентации, а не в той, что видна в редакторе.

Исправлено добавлением трёх полей (`flippedHorizontally/Vertically/Diagonally`) в `ResolvedTile` (`TiledLevel.h`) — флаги читаются из сырого GID до маскирования и сохраняются вместе с уже резолвленными текстурой/вырезом. При отрисовке (`spawnTiledTileAt` в `SceneFacade.cpp`) они превращаются в поворот/масштаб спрайта:

- Без диагонального флага — обычное независимое отражение по осям: `setFlippedX(H)`, `setFlippedY(V)`.
- С диагональным флагом (транспонирование тайла по главной диагонали, применяется по спецификации Tiled раньше H/V) — поворот на 90° плюс `setFlippedX(V)`, `setFlippedY(!H)`. Эта комбинация не была очевидна — угол поворота и то, что вместо своих же H/V-флагов используются местами переставленные V/!H, подобраны перебором всех 8 комбинаций поворота на 90°×масштаб и сверены с эталонным разбором (диагональ → H → V) попиксельно, а не выведены аналитически на бумаге.

### Выбор пункта меню — курсор перехватывает клавиатуру

`MenuOverlayComponent::updateMouse()` каждый кадр проверял, не находится ли курсор над одной из кнопок, и если да — молча переключал `m_selected` на неё, даже если курсор просто «отдыхал» там с прошлого экрана, а не был осознанно наведён игроком. На практике это давало осмысленный баг: после ввода имени на экране победы Enter активировал не «Играть заново» (первый пункт по умолчанию), а тот пункт, над которым случайно оказывался курсор. Исправлено двумя изменениями: во-первых, `updateMouse()` теперь двигает выбор только при реальном изменении позиции курсора между кадрами, а не при самом факте попадания в границы кнопки; во-вторых, на первом кадре после появления меню (переход invisible → visible) компонент запоминает текущую позицию курсора как «уже учтённую» и синхронизирует `KeyEdge`, не давая тому же физическому нажатию Enter, которым подтвердили предыдущий экран, тут же активировать первый попавшийся пункт этого меню.
